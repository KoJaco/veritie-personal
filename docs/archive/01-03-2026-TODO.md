## 3. feat/context-rail-resolver (done)

- rail config resolver...

I'm planning this as a registry that returns rail config (enabled, showTrigger, defaultTab, tabs (array of RailTab, getContext callback for the assistant tab which returns type AssistantContext)). RailTab type is something like { key: "assistant" | "evidence" | "activity" | "metadata" | "recent"; label: string, render: () => ReactNode}.

The route will supply context, resolver supplies the UI -> so the route must supply routeId or pathname, the primaryObject (type & id), any loaded data for evidence/acitvity stubs -> resovler returns a set of tabs and what to render. This means that the rail must be implemented at the global layout level, not the page level (AppShell). Trigger is visible unless the route opts out.

Keep components generic (EvidencePanel({scope}), ActivityPanel({scope})) where scope could be multiple objects, like "task", "artifact", "evidence", etc. This allows reuse across routes and means that the primary 'object' in question drives most of the UI logic -> if the primary object is task, then include evidence + activity... if no object, just include assistant + recent activity.

Assistant is always first tab and obvious

I can always scope this down if we're pushed for time with the MVP.

- Document ADR, decision, contracts, etc.
- Tabs per route something like this:
    - Task -> Assistant | Evidence | Activity
    - Artifact or Object -> Assistant | Activity
    - Evidence -> Assistant | Activity | Metadata
    - Dashboard -> Assistant | Recent Activity
    - Connections -> Assistant

    Default tab is Assistant, rail hidden on onboarding/auth

Deliverable:

- One rail, many contexts (kind of like a task driven UI but for the assistant / context rail)

## 7. feat/evidence-upload-preview

Ability to upload evidence and preview it post upload.

I am assuming we're supporting the following file formats for evidence uploads:

1. Docs (PDF, DOCX, TXT, Markdown) - policies, reports, exports.
2. Spreadsheets (XLSX, CSV) - access lists, vendor lists, risk registers.
3. Images (PNG, JPG, JPEG) - screenshots, dashboard shots, MFA settings.
4. Logs (JSON, TXT) - security exports, config dumps.

Not supporting:

- Videos (MP4, AVI, MOV) - not supported yet
- Audio (MP3, WAV, AAC) - not supported yet
- Code (JS, TS, Python) - not supported yet

Storage strategy:

- Blob storage for files
- Store file metadata in DB
- Extract text in the future
- Attach evidence to tasks via join table (confirm with Matt)

Preview strategy:

- in our detail page we have inline previews for evidence (no blocking layout).
- We have a modal for full screen previews (zoom, scroll, multi-page)

Upload strategies:

- Next/Image.. generate thumbnail variants, click -> modal/lightbox full size... optionally show EXIF metadata in rail?
- For PDFs, I think we should use react-pdf (wrapper around pdf.js)... consistent rendering, page-by-page control, zoom, etc.
- .docx.... if we're supporting this, probably convert and save copy to pdf on upload (azure function -> convert DOCX -> pdf -> store PDF version)...
- .xlsx -> convert to PDF on upload (same as docx).
- .csv -> prase server-side, render preview table (first N rows), allow download full.
- Markdown solved

Security considerations:

- We should be never rendering arbitrary HTML from docs.
- Trust file ext over MIME
- Allow embedded JS (PDF could contain JS)
