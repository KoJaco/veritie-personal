# Architecture Questions - Responses

## A. Assistant UI & Artifact Format

### Q1 - Canonical artifact format for MVP
**Choice:** Markdown + Blocks JSON

**Justification:** Store markdown as the source of truth in PostgreSQL, convert to blocks JSON on-demand for rendering with comment anchoring. This gives us flexibility to support inline comments later while keeping LLM output simple and the backend lean for MVP.

### Q2 - Inline comments – timing & depth
**Choice:** Not in MVP

**Justification:** Comments add significant complexity (anchoring, conflict resolution, UI state) that conflicts with our 16-week launch timeline. Users can provide feedback through the chat assistant or task comments, which covers 80% of collaboration needs for early customers.

### Q3 - Backend LLM output contract
**Choice:** Markdown only

**Justification:** Backend stores markdown; frontend handles conversion to blocks JSON for rendering when needed. This keeps the API simple, allows us to swap rendering strategies later, and avoids dual-format storage overhead.

### Q4 - Change management expectations
**Choice:** Version-based audit only (v1, v2, v3)

**Justification:** Simple append-only versioning with metadata (author, timestamp, changeSummary) gives us audit trail and rollback without the complexity of track-changes UI. We can add git-style diffs in the UI later using standard markdown diff libraries.

### Q5 - Is raw HTML allowed in LLM output?
**Choice:** No (markdown-only)

**Justification:** HTML introduces XSS risks and complicates sanitization; markdown-only keeps the attack surface minimal and rendering predictable. If we need rich formatting later, we extend markdown syntax (e.g., custom blocks) rather than allowing arbitrary HTML.

## B. Assistant Scope & Capabilities

### Q6 - Assistant permissions in MVP
**Choice:** Generate artifacts + Q&A

**Justification:** The core value prop is AI-generated policies/checks/roadmaps, so artifact generation is non-negotiable for MVP. Q&A provides context-aware help, making the assistant genuinely useful rather than just a chatbot.

### Q7 - Chat persistence
**Choice:** Stored per task/object

**Justification:** Scoping chats to tasks/artifacts lets users resume context when they return to work on a specific item. Fully persisted audit trail can come later; ephemeral would lose too much value when users navigate away.

### Q8 - Context injection rules
**Choice:** Automatically inject: Task + Artifact content + Evidence metadata

**Justification:** Task gives the assistant goal context, artifact content enables intelligent edits/suggestions, and evidence metadata helps the assistant understand what's missing or needs review. Policy memory can be added post-MVP when we have usage patterns to inform retrieval strategy.

## C. Context Rail Behavior

### Q9 - Which routes MUST show the assistant rail in MVP?
**Choice:** Dashboard/Work + Task + Artifact/Object + Evidence

**Justification:** These are the core workflows where AI adds value (generating artifacts, answering compliance questions, evaluating evidence). Settings and onboarding don't need AI assistance and would just add UI clutter.

## D. Tenancy & Auth

### Q11 - User tenant relationship
**Choice:** One tenant per user (assumed)

**Justification:** Early-stage startups (target market) don't need multi-org switching in MVP; one team per company keeps UX simple. We can add org-switching post-launch if agencies/consultants request it.

### Q12 - How tenant is identified by the API
**Choice:** JWT claim

**Justification:** Already implemented in the backend (AuthMiddleware extracts tenant_id from JWT claims); this is the most standard approach and works seamlessly with our existing FastAPI setup. No subdomain routing or header complexity needed.

## E. Audit Model

### Q13 - Audit storage model
**Choice:** Version snapshots only

**Justification:** For MVP, versioning artifacts/tasks/evidence on mutation gives us compliance audit trail without append-only event sourcing complexity. We can add granular event logs later if SOC 2 requires it.

### Q14 - What is auditable in MVP
**Choice:** Artifacts + Evidence + AI outputs (model, prompt context)

**Justification:** These three cover the compliance use case (what was generated, who uploaded what, which AI model/prompt was used). Tasks and comments can use simpler updated_at timestamps for now.
